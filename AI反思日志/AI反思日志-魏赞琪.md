## AI 帮忙解决了什么

### 1. 测试目录职责和覆盖范围梳理

我负责测试和 API 对接后，最先需要弄清楚 `tests/` 目录里每个测试文件覆盖的对象。AI 帮我把测试文件按功能归类：`test_agent_tool_registry.py` 关注工具注册，`test_mcp_client.py` 和 `test_mcp_tool_registry.py` 关注 MCP 接入，`test_memory_rag.py` 关注长期记忆和检索，`test_multimodal_cleaner.py` 关注多模态清洗，`test_knowledge_library_search.py` 关注知识库搜索，`test_task_scheduler.py` 关注模型调度器。

这个整理让我不用逐个文件盲读。测试文件本身数量不算多，但它们对应的后端模块跨度很大。AI 先帮我建立测试地图，我再回到代码里确认每个测试为什么存在，哪些测试能作为质量门禁的证据。

### 2. API 对接链路定位

AI 帮助我梳理了前端 API client 到后端 REST 路由的对应关系。前端 `console/src/api/client.js` 负责统一请求、错误处理和 SSE 解析，`agent.js` 负责 Agent 流式对话，`session.js` 负责会话和消息历史，`settings.js` 负责用户设置和自定义记忆。后端对应的路由主要在 `agent_service/api/rest/agent.py`、`sessions.py`、`settings.py` 和 `health.py`。

这个链路对我做 API 对接很重要。接口问题经常不会只出现在一个文件里，前端字段名、请求路径、后端参数校验、返回结构都有可能引起错误。AI 把这些文件放在同一条请求链路里解释，帮助我更快找到排查顺序。

### 3. SSE 流式接口的测试思路

`/agent/stream` 和普通 JSON 接口差别很大。AI 帮我明确了它的验证重点：前端不能只看最终回答，还要看每段 `data:` 事件能否被持续解析，结束标记是否正确，异常事件是否能进入错误处理路径，中途取消时是否能释放请求。

这部分帮助我理解了 `streamLines` 的意义。它把底层 ReadableStream 解析成前端可消费的事件对象。测试和讲解时，不能只说“调用了接口”，还要说明这个接口为什么要按流来处理。

### 4. 边界场景设计

质量门禁要求列出极端输入并测试修复。AI 帮我把 API 对接中更常见的边界场景列出来，包括缺少 `user_id`、空 prompt、无效 `session_id`、非法 limit、设置内容为空、SSE 中途断开、模型 key 未配置、知识库搜索 query 为空。

我没有直接使用 AI 给出的全部场景，而是挑选了当前项目里能解释、能复现、能和代码对应上的内容。这样写进报告时更有说服力，也方便现场答辩。

### 5. 压测脚本和验收材料整理

Sprint 2 要求使用 wrk 或 Locust 测 API。AI 帮我设计了 Locust 压测方案，并把压测对象限定在非模型接口，例如 `/health`、`/sessions`、`/agent/tools`。这些接口能体现后端路由、服务依赖和基础读操作性能。

AI 同时帮我整理了压测命令、CSV 导出方式和报告模板。实际使用时还要看本机环境是否安装 Locust，后端是否已经完成启动，`/health` 是否稳定返回。这个过程让我认识到，压测材料不能只写命令，还要说明测试对象和指标口径。

### 6. API 集成测试与断言设计

AI 帮我把 API 对接测试拆成三个层次。第一层是前端 API client 和后端 REST 路由的参数对应关系，重点检查路径、请求方法、query 参数和 body 字段是否一致。第二层是后端接口返回结构的断言验证，重点检查状态码、必填字段、错误信息和列表结构。第三层是 REST 与 gRPC 的能力对照，确保同一类功能在两套接口中保持一致。

这个过程让我理解到，API 测试不能只看接口有没有返回。更重要的是用断言证明返回内容符合前端读取方式，也符合 proto 中定义的数据结构。比如会话列表接口要验证返回数组中是否包含 `session_id`、`user_id`、`session_name`、`created_at` 和 `updated_at`，错误输入时也要检查状态码是否符合预期。

## AI 没帮上忙 / 做错了什么

### 1. 初始测试建议过于分散

AI 一开始会把所有模块都列进测试范围，包括 AgentCore、RAG、知识库、多模态、MCP、调度器、安全审核和前端组件。这个范围对项目整体有帮助，但对我负责的测试和 API 对接来说太分散，也不方便形成可执行的测试维护计划。

后来我手动收缩了重点。后端测试以 `tests/` 目录为主，优先关注 AgentCore、工具注册表、知识库搜索、多模态清洗和任务调度这些已有测试可以支撑的模块。前端对接以 `console/src/api` 和 `editor/src/api` 为主，接口说明以 REST、SSE 和 gRPC 对照为主。这样内容更符合我的实际职责。

### 2. AI 容易忽略测试不能调用真实模型

项目规范要求测试不能连接真实外部模型 API。AI 有时会建议直接调用 `/agent/test` 或 `/agent/stream` 做完整验证，但这会依赖模型 key、网络和模型服务状态。这样的测试不稳定，也不适合作为自动化测试。

我后来把真实模型接口和普通自动化测试分开处理。自动化测试尽量使用 fake、mock 或稳定输入。模型连通性单独作为手工验证或脚本验证，不混进常规 pytest。

### 3. 压测目标需要人工筛选

AI 可以快速生成 Locust 脚本，但一开始没有充分区分轻量接口和模型接口。`/agent/stream` 是项目核心接口，但它的耗时主要来自模型生成。如果拿它做 100 并发 200ms 指标，结果会被外部模型影响。

我最后选择轻量 REST 接口做性能门禁。模型流式接口保留为首包时间、断流处理和稳定性观察。这样报告更符合技术逻辑，也更容易向老师解释。

### 4. 环境问题不能只靠 AI 判断

AI 给出的命令在文本上正确，但实际运行时会遇到本机缺依赖、端口未启动、用户级 Python 路径不可见、后端首次下载模型等问题。比如 Locust 安装后，普通命令可能找不到模块，需要确认实际 Python 环境。

这些问题必须通过终端输出判断。AI 能给出方向，最终还要看命令结果、日志、端口状态和接口返回。

## 踩过的坑

### 1. 把接口测试和模型连通性混在一起

坑：一开始容易觉得只要 `/agent/stream` 能返回内容，就说明 API 对接没问题。但这个接口会进入 AgentCore 和模型调用，失败原因可能来自模型 key、外部网络、调度器或上下文构建。它不能完全代表接口层质量。

教训：接口测试要分层。轻量 REST 接口用于验证路由、参数和返回结构，SSE 接口用于验证流格式，模型连通性单独验证。分层之后，问题定位会清楚很多。

### 2. SSE 不能用普通 JSON 方式解析

坑：普通接口可以用 `response.json()` 处理，但 SSE 是持续文本流。每一段事件以 `data:` 开头，直到 `[DONE]` 才结束。如果按普通 JSON 接口理解，前端就无法逐步显示回复。

教训：测试和讲解 SSE 时，要关注流式读取、事件分段、结束标记和异常事件。`streamLines` 是 API 对接中的关键函数。

### 3. 测试文件名能说明测试职责

坑：刚开始看 `tests/` 时，只知道它们是测试文件，但没有把文件名和后端模块对应起来。这样答辩时容易只说“我们有测试”，讲不出每个测试证明了什么。

教训：测试文件要按职责讲。比如工具注册测试证明工具 schema 稳定，MCP 测试证明外部工具接入逻辑，RAG 测试证明检索链路，多模态清洗测试证明输入文件处理能力，任务调度测试证明队列、重试和熔断逻辑没有回退。这样质量门禁材料更具体。

### 4. 断言不能只检查请求成功

坑：接口联调时，容易只看请求有没有 200，或者前端页面有没有显示结果。这样会漏掉字段结构错误、状态码不准确、错误信息格式不统一等问题。比如返回数组正常，但数组元素缺少前端需要的字段，页面后续仍然可能出错。

教训：API 集成测试要写明确断言。状态码、返回字段、错误 detail、数组长度、关键 ID 和时间字段都要检查。REST 和 gRPC 对同一功能的返回语义也要对照确认。

### 5. Windows 下压测工具选择要现实

坑：wrk 在 Windows 环境里通常没有现成命令。直接按 Linux 常见写法准备，现场很容易卡住。Locust 更适合当前环境，但也要确认安装位置和启动方式。

教训：压测命令尽量使用 `python -m locust`。这种写法对 PATH 依赖更少，适合机房电脑。压测前先访问 `/health`，确认后端已经可用。

### 6. 首次启动后端会影响压测结果

坑：项目后端启动时可能下载或加载 embedding、rerank 模型，还会初始化知识库和服务。如果这时直接开始压测，结果会出现超时或连接失败。

教训：压测要在服务稳定后进行。启动完成后先检查 `/health`，再跑 Locust。报告里也要说明首次模型初始化不计入 API 响应时间。

## 学到的经验

### 1. 测试的价值在于证明边界

正常路径成功只能说明功能大体可用。质量门禁更关注边界场景，例如参数缺失、非法 ID、空输入、连接中断和依赖不可用。测试要能证明这些情况下系统不会直接崩溃，并且能返回可解释的错误。

这让我对 `tests/` 目录的理解更明确。测试不是给代码做装饰，它要为验收提供证据，也要为后续修改提供保护。维护测试时，需要关注已有测试是否还能覆盖当前实现，接口字段变化后也要同步更新断言。

### 2. API 对接要看完整链路

前端 API client、后端 REST 路由、Service 层和 gRPC proto 之间是连续的。某个接口出错时，不能只看前端，也不能只看后端。路径、参数、字段名、返回结构和错误格式都要检查。

我学到的排查顺序是先看前端请求路径，再看后端路由定义，然后看依赖注入和服务方法，最后检查返回结构是否符合前端读取方式。

### 3. 单元测试和集成测试关注点不同

单元测试主要验证模块内部逻辑，例如工具注册表能否生成稳定 schema，多模态清洗能否处理不同文件类型，任务调度器能否执行重试和熔断。集成测试更关注接口层能否把前端请求、后端路由、服务返回和协议字段连起来。

这两类测试不能互相替代。单元测试帮助定位内部逻辑问题，API 集成测试帮助发现参数不一致、状态码异常和数据格式错误。

### 4. 自动化测试和手工验证要分开

自动化测试应该稳定、可重复，尽量不依赖真实模型和外部网络。手工验证可以覆盖模型连通性、SSE 真实流式效果、前端页面展示和压测截图。

这两类验证目标不同。自动化测试保证基础逻辑不回退，手工验证保证真实运行链路能交付。

### 5. 压测报告要说明测试口径

压测不是只给出一个平均响应时间。报告里要说明并发用户数、爬升速率、持续时间、接口范围、失败率、P95 和 RPS。还要说明哪些接口没有纳入指标，以及原因。

对这个项目来说，轻量 API 可以用 100 并发响应时间评价。模型流式接口更适合按首包时间和稳定性评价。这个口径清楚后，报告才更可信。

### 6. AI 更适合做测试规划和材料初稿

AI 在测试和 API 对接上的帮助主要体现在三点：快速读代码、整理测试范围、生成报告初稿。它能提升准备效率，但不能替代实际运行。

最终结果仍然要靠我确认。测试是否真的覆盖了边界，接口是否真的返回，压测是否真的跑完，报告是否符合验收要求，都需要结合项目代码和运行结果判断。
