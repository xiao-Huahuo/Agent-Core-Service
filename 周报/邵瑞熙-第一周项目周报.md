**二、本周完成工作**

*   **目标达成情况：**
    1. Agent 图执行与会话消息持久化：已完成。完成了 `AgentCore` 作为后端业务门面的主要逻辑，图结构可以围绕安全审核、规划、模型决策、工具调用、观察和压缩节点进行流式执行。
    2. RAG 长期记忆与上下文构建：已完成。完成了 `ContextBuilder`、长期记忆服务和统一召回链路，使 Agent 在会话运行前可以读取短期历史、长期记忆索引和知识库索引。
    3. 工具注册表与 MCP 接入：已完成。完成内置工具注册、工具执行器、MCP 工具适配层，并让 AgentCore 通过同一套注册表获取最终工具能力。
    4. 长期规则工具：已完成。新增 `write_long_term_rule`，使 Agent 可以在用户明确要求长期遵守规则时写入用户系统提示词条目。

*   **具体完成任务列表：**
    *   **后端 Agent 流式入口：** 完成 `/agent/stream` 的 GET 与 POST 两种入口。接口层接收 `prompt`、`user_id`、`session_id` 和可选引用文本，交给 `AgentCore.stream_session_prompt()` 执行，并通过 SSE 事件流返回 token、节点事件、工具轨迹和错误信息。POST 入口用于承载较长引用文本，避免 URL 长度限制影响引用链路。

    *   **AgentCore 图执行主流程：** 完成 AgentCore 初始化和运行入口。AgentCore 负责加载配置、检查本地模型、构建 LangGraph、创建工具注册表、读取用户模型配置、设置运行时工具上下文，并把图执行事件整理成前端可观测的数据。一次用户提问进入后，会先由上下文构建器生成 LangChain messages，再进入图执行线程。图执行中，planner 给出探索建议，agent 节点决定是否调用工具，action 节点执行工具，observation 节点审视工具结果并决定继续探索或回到 agent 输出最终答复。

    *   **会话与消息持久化：** 完成 `SessionService` 和 `MessageService` 的业务服务。SessionService 负责会话创建、查询、重命名、删除和状态保存。MessageService 负责保存用户消息、系统上下文、assistant 回复、工具调用和工具结果。这样 Agent 的一次回答不只是临时模型调用，还会被记录为可恢复的会话过程。

    *   **上下文构建与记忆召回：** 完成 ContextBuilder 的主要逻辑。它会读取同一 session 的近期消息，过滤孤立工具消息，并在当前用户问题前注入长期记忆和知识库召回索引。对于用户引用的文本，ContextBuilder 会把引用材料和用户问题组合成同一条 HumanMessage，使引用内容真实进入模型上下文。

    *   **长期记忆服务：** 完成统一长期记忆表和服务层。长期记忆可以保存会话摘要、重要事实和知识库切片，并带有 tag、memory_type、source、hash、confidence、importance 等字段。召回层可以按用户和 session 进行检索，供 ContextBuilder 或 Agent 工具使用。

    *   **工具注册表与工具执行器：** 完成 `ToolRegistry` 和 `ToolExecutor`。内置工具以统一工具定义注册，之后转换成 LangChain StructuredTool 绑定给模型。模型生成 tool_calls 后，ToolCallNode 通过 ToolExecutor 查找并执行对应工具，再把执行结果写回 ToolMessage，供下一轮 agent 节点继续推理。

    *   **MCP 工具扩展：** 完成 MCP Client 和 MCP 工具注册适配器。MCP Client 支持 stdio 型 MCP Server 的连接、初始化、工具列表拉取和工具调用。适配器会给外部工具生成带 server 前缀的注册名，避免和内置工具冲突，并把 MCP 工具包装成当前 ToolExecutor 可以执行的同步 callable。

    *   **长期规则工具：** 完成 `write_long_term_rule`。该工具把用户要求长期遵守的规则写入 `UserSystemPromptEntry`，效果与设置页手动添加系统提示词一致。模型决策节点每次调用时都会读取用户自定义系统提示词并追加到系统消息中。长期规则与长期记忆的语义不同，前者每轮必注入，后者按相关性召回。

    *   **Agent 运行错误修复：** 修复 small-tier 模型调用未继承用户 LLM 配置导致的连接错误。输入审核、规划、观察、上下文压缩和自动命名等小模型调用会优先读取用户配置，并在小模型 key 为空时回退到主模型配置。错误信息也从裸连接异常调整为更可读的限流、缺 Key、连接失败等提示。

一次完整提问的运行路径可以概括为：前端发送 session 级请求，REST 层建立 SSE 响应，AgentCore 调用 ContextBuilder 组装历史消息、引用材料、长期记忆索引和知识库索引，随后把消息输入 LangGraph。图中先经过安全审核和策略规划，再由模型决策节点决定直接回答或调用工具。若模型选择工具，action 节点执行 ToolExecutor，结果以 ToolMessage 回到图状态，observation 节点判断信息是否足够。信息不足时继续回到 planner 和 agent，信息足够时回到 agent 输出最终回答。执行期间的 user、system、assistant、tool 消息会写入消息服务，部分图状态也会进入 session 状态字段，用于后续轮次恢复。

**三、未完成工作及原因**

*   **未完成任务列表：**

    *   **原因：** 当前周内优先保证 Agent 可运行链路、工具调用链路和长期记忆链路稳定。引用溯源的后端数据结构已有基础，但前后端展示协议还需要细化，短期内不适合和主链路稳定性一起大幅改动。

    *   **回答 citation 锚点：** 尚未实现类似 `[1]`、`[2]` 的答案内来源锚点。
    *   **原因：** 该功能需要模型输出格式、后端 citation 解析、前端渲染和点击跳转共同配合。实现本身不复杂，风险主要在输出格式不稳定，容易影响正常回答展示。

    *   **Agent 输出渲染异常修复：** 部分 HTML 或代码块输出在前端渲染时仍可能出现乱码或卡顿。
    *   **原因：** 该问题定位方向比较明确，主要是前端渲染和内容清洗边界处理。它和本周负责的 Agent 后端主链路相关性较低，因此没有放在优先级最高的位置。

    *   **多轮对话后卡顿排查：** 长会话下 Agent 页面性能仍需进一步分析。
    *   **原因：** 当前后端已经支持上下文窗口和压缩触发，但前端消息列表、观测事件、工具轨迹渲染可能共同造成压力。该问题需要结合性能面板和真实长会话样本处理。

整体来看，未完成项主要集中在体验增强和结果展示层。它们并不阻断 Agent 的基础运行链路，但会影响验收时对可解释性和长时间使用体验的观感。下周需要把这些功能拆成较小的接口协议和 UI 渲染任务，避免一次性修改过多模块。

**四、遇到的问题与困难**

*   **技术问题：**
    *   **Agent 图链路较长，错误来源不容易定位。** 一次用户请求会经过 REST、ContextBuilder、LangGraph、LLM 调度器、工具执行器、消息服务和记忆服务。早期出现连接错误时，前端只能看到 `Connection error`，无法判断是 API Key 缺失、模型限流、Base URL 配置错误，还是小模型调用没有继承用户配置。
    *   **已尝试的解决方案：** 将用户 LLM 配置在图执行前一次性读入 state，并让 planner、observation、安全审核、压缩和自动命名等小模型调用共享同一套配置。错误处理层增加限流、缺 Key、连接失败、内容安全拦截等分类提示。这样日志可读性和前端错误提示都更稳定。
    *   **需要帮助或待解决：** 暂无外部阻塞。后续可以继续补充更细的 request id 和节点级耗时统计，方便定位慢调用。

*   **技术问题：**
    *   **长期记忆和长期规则容易混淆。** 长期记忆是可召回信息，模型可能读取，也可能因为相关性不足而不读取。长期规则属于系统提示词，用户一旦要求长期遵守，Agent 每轮都应该读到。
    *   **已尝试的解决方案：** 将长期规则设计为 `write_long_term_rule` 工具，写入用户系统提示词条目。长期记忆仍保留 `write_long_term_memory` 和 RAG 召回机制。两者在存储表、注入位置和使用语义上分开，减少模型行为的不确定性。
    *   **需要帮助或待解决：** 后续需要在前端设置页和 Agent 工具说明中继续强化这一区分，避免用户把临时偏好误写成必须遵守的系统规则。

*   **技术问题：**
    *   **工具注册来源变多后需要统一观测。** 项目内置工具、知识库工具、文件工具和 MCP 工具都可能进入同一 Agent。若只按来源单独展示，验收时很难说明模型最终能调用哪些工具。
    *   **已尝试的解决方案：** 让 `ToolRegistry` 成为最终注册表，AgentCore 提供 `list_registered_tools()`，REST 层开放 `/agent/tools`。这样观测页面可以从最终注册结果读取工具数量、名称、说明和参数 schema。
    *   **需要帮助或待解决：** 暂无。MCP 当前以 stdio 工具为主，后续如果加入 HTTP 或远程鉴权型 MCP Server，还需要扩展配置校验和连接生命周期管理。

*   **非技术问题：**
    *   本周一个人完成了原本按多人拆分的 Agent 后端业务任务，实际工作密度较高。设计、实现、修复和文档准备之间切换频繁，容易造成阶段性上下文负担。
    *   **已采取的措施：** 通过 CHANGE_HISTORY、TODO 和 commit 拆分记录功能进展，把大功能拆成 AgentCore、ContextBuilder、工具注册表、长期规则等相对独立的验收点。后续继续保持小块提交和明确说明，减少临近验收时的追溯成本。

**六、心得体会与学习收获**

*   **本周学习到的新知识和技能：**
    *   对 LangGraph 的工程化使用有了更完整的理解。图节点本身并不难，难点在于如何让节点之间传递足够稳定的业务状态，并把工具调用、错误处理、流式输出和消息持久化接在同一条链路里。单独看每个节点都能运行，不代表整个 Agent 能在真实会话里稳定运行。
    *   对 RAG 上下文构建的边界有了更清晰的认识。长期记忆、知识库片段、当前 session 历史和用户引用材料都可以进入模型上下文，但它们的优先级和注入方式不同。直接把所有内容塞进 prompt 会让回答变重，也会让模型忽略真正关键的信息。当前实现采用索引提示和工具取全文结合的方式，能在上下文长度和可解释性之间取得比较稳妥的平衡。
    *   对工具注册表的价值有了更明确的判断。Agent 能调用工具只是第一步，更重要的是所有工具都能被统一注册、统一执行、统一观测。MCP 接入后，工具来源会继续增加，如果没有最终注册表，调试和验收都会变得混乱。

*   **对项目或开发流程的思考：**
    *   Agent 系统的后端基础设施需要比普通接口更重视链路说明。普通接口只要输入输出稳定即可，但 Agent 的一次请求会包含模型决策、工具调用、记忆召回和多轮循环。验收时如果只能说某个接口能返回答案，说明力度不足。更合理的方式是从一次用户提问出发，说明 session 如何创建，消息如何进入上下文，图如何执行，工具如何被调用，记忆如何被召回，结果如何回到前端。

    这也是本周后半段整理 commit 和文档时最大的感受。代码实现完成后，还需要把工程事实转化成可讲述的结构。比如 `write_long_term_memory` 和 `write_long_term_rule` 的区别，在代码里只是两个工具，在验收解释中却关系到 Agent 是否能区分可召回事实和必须遵守规则。

*   **自我改进方面：**
    *   后续需要继续提高任务切分粒度。AgentCore、ContextBuilder、ToolRegistry 和长期规则这几个模块已经比较清楚，但部分修复性 commit 仍然可能混入多种内容。验收要求按功能独立 commit 时，应该让每次提交都能回答三个问题：解决了什么问题，改了哪条链路，如何验证。
    *   还需要进一步控制复杂功能的实现顺序。Agent Loop、引用溯源和对话中断都容易牵动多个模块。下周应先确定接口协议，再做后端状态流转，最后接前端展示。这样可以降低返工概率，也方便在验收前保留稳定版本。
