**一、基本信息**

* **项目名称：** MetaWeave
* **当前项目阶段：** 核心功能开发、联调与稳定性修复阶段
* **本周总工时：** 44 小时

本周工作继续围绕后端 `agent_service/` 展开，重点从第一周的基础链路搭建转向执行模式拆分、状态机强化、工具调度约束、上下文压缩、引用溯源、安全审核接入和知识库检索作用域修复。第一周主要解决 Agent 能够跑通的问题，本周主要解决 Agent 在复杂任务、长会话、知识库召回和可解释输出中的稳定性问题。

同时，配合知识库文件、上传、屏蔽区和惰性灌库等功能，对 RAG 检索服务的向量写入、用户隔离、文件级入库、屏蔽清理和召回引用链路进行了维护。相关改动均与 `CHANGE_HISTORY.md` 中 7 月 12 日至 7 月 16 日的 Agent Loop、引用锚点、自动 RAG、灌库流程和 OCR 语义修复保持一致。

**二、本周完成工作**

* **目标达成情况：**
    1. Agent 执行模式拆分与 auto 路由：已完成。完成 simple、react、plan 三类执行链路，并将 auto 模式从本地关键词判断调整为小模型分类入口。
    2. Planner 与 Observation 状态机强化：已完成。plan 模式下支持子问题状态、观察决策历史和 continue、answer、retry、abandon 四类分支。
    3. 工具调用稳定性与上下文控制：已完成。限制单轮工具调用数量，压缩历史 ToolMessage，降低长文件和联网检索结果造成的上下文膨胀。
    4. 引用溯源与 RAG 作用域修复：已完成。自动 RAG 与知识库工具统一进入 citation_map，并按用户当前知识库作用域召回。
    5. 安全审核链路维护：已完成。simple、react、plan 模式均保留输入审核、意图审核和输出审核节点，避免模式拆分后绕过安全节点。

* **具体完成任务列表：**
    * **AgentCore 多模式编排：** 在 `AgentCore` 中同时维护 plan 图和 react 图，并为短问直答保留 simple 路径。simple 用于极短闲聊和明显不需要工具的请求，保留 ContextBuilder 和消息持久化。react 图保留 safety、agent、action、output 审核链路，工具结果直接回到 agent 节点。plan 图保留 planner、agent、action、observation 的完整循环，面向多步骤分析、资料核验和复杂任务。

    * **auto 模式小模型分类：** 将 auto 路由从硬编码关键词规则调整为 small tier 分类。分类结果限定为 simple、react、plan。模型能力不足、不确定、需要事实核验、需要外部信息时，路由策略至少选择 react。若小模型调用失败或输出不可解析，再回退本地规则。该改动减少了简单问题进入 plan 图导致的额外 LLM 调用，也降低了复杂问题被误判为直答的风险。

    * **Planner 节点状态管理：** 强化 plan 模式下 planner 的状态表达。planner 输出包含 `sub_questions`、`current_index`、`status` 等字段，并读取 observation 决策历史，避免每轮重新规划造成方向漂移。对于需要连续检索、阅读文件、整理结论的任务，planner 可以保留当前子问题位置，后续节点按照状态继续推进。

    * **Observation 节点决策维护：** 将 observation 从普通总结节点改为结构化决策节点。每轮工具执行后，observation 会给出继续探索、进入最终回答、重试工具或承认边界四类结果。LangGraph 根据该结果决定回到 planner、回到 agent、重试工具或生成边界说明。这样可以减少无效循环，也让复杂任务的执行路径更容易观测。

    * **工具注册表与执行调度约束：** 继续维护 ToolRegistry 和 ToolExecutor 的统一调度方式。内置工具、知识库工具、文件工具和外部工具在进入模型前保持统一 schema。为避免模型单轮同时触发过多工具调用，action 节点增加单轮最多 4 个工具调用的限制，超出部分以 deferred ToolMessage 形式留给下一轮处理。该策略对读取多份文件和批量检索类任务影响明显，能控制上下文与请求压力。

    * **长期记忆与短期上下文压缩：** 对模型入参前的 ToolMessage 进行压缩。最近工具结果保留较多摘要，旧工具结果压缩为更短文本，减少长文件、搜索结果和知识库片段持续累积导致的 token limit 错误。ContextBuilder 继续负责短期会话历史、用户自定义系统提示词、长期记忆索引和知识库召回索引的组装。

    * **RAG 引用溯源链路：** 完成自动 RAG 与知识库工具召回结果的统一挂载。召回片段进入 `citation_map`，工具结果生成 `K1`、`K2` 类型引用号，最终 assistant 消息只保存正文实际使用过的引用。历史消息按自身 metadata 渲染来源，避免旧消息复用当前轮的全局来源。

    * **RAG 用户作用域修复：** 修复自动 RAG 注入知识库时默认落到 `system` 知识库的问题。`ContextBuilder._build_retrieved_context()` 调用 `retrieve_knowledge_with_debug()` 时传入当前 `user_id`，使召回结果来自当前用户与当前知识库配置。新增回归测试覆盖该参数，防止后续修改再次丢失用户隔离。

    * **知识库向量写入与惰性灌库维护：** 配合知识库文件流程，维护文件级入库、全量入库、上传后是否自动入库、屏蔽区清理和 stale source 删除逻辑。上传文件默认只进入 active 知识库目录，按用户设置决定是否触发单文件灌库。全量灌库与单文件灌库均会遵守屏蔽规则，屏蔽文件对应的 frontmatter 和向量切片会被清理。

    * **多模态入库基础维护：** 对图片 OCR、PDF 文本层提取和 PaddleOCR 模型预热相关链路进行维护，使图片、PDF 与普通文本在进入知识库前能够返回更准确的状态。后端新增 skip reason 和 status message，用于区分不支持后缀、屏蔽、OCR 无文字、OCR 引擎不可用和无可入库切片等情况，避免前端把 0 chunk 统一显示为入库失败。

    * **安全审核节点集成：** 在模式拆分后重新确认安全链路位置。simple 路径保留输入侧约束与输出审核，react 和 plan 图保留 safety、意图审核、工具执行前后的状态约束以及输出审核。这样可以保证不同执行模式在能力和成本上有差异，但不会因图结构变化跳过敏感词检测、意图审核或最终输出审核。

    * **流式执行与中断支持：** 后端在阻塞 LLM 调用前发送轻量 trace，避免前端长时间无反馈。用户中断本轮输出后，当前用户输入、已产生的思考轨迹和可保留的上下文仍会进入后续会话，减少中断后上下文断裂。该能力对长任务和联网检索类任务尤其重要。

本周完成后的典型链路为：请求进入 `AgentCore.stream_session_prompt()` 后，先由 ContextBuilder 组装短期历史、长期记忆、知识库召回和用户规则。若用户选择 auto，则 small tier 先判断执行模式。simple 直接流式回答，react 进入 agent 与 action 循环，plan 进入 planner、agent、action、observation 状态机。工具结果通过统一注册表执行，RAG 结果进入 citation_map，最终回答经过输出审核后保存消息与已使用引用。

**三、未完成工作及原因**

* **未完成任务列表：**
    * **RAG 重排序策略仍需补充实测：** 当前检索链路已支持向量写入、embedding 查询和召回调试信息，引用挂载也已完成。重排序仍主要依赖现有分数与召回结果排序，缺少覆盖不同文档类型、长短 query 和多语言内容的稳定评测集。
    * **原因：** 本周优先处理 Agent Loop 拆分、引用溯源和用户作用域修复。重排序评测需要准备固定样本、标注预期片段和对比指标，临时加入会降低结论可信度。

    * **MCP 工具远程鉴权链路未扩展：** 本周继续维护统一工具注册和执行调度，MCP 仍以当前可用工具形态为主，没有扩展远程鉴权、连接保活和失败隔离策略。
    * **原因：** 现阶段验收重点在内置工具、知识库工具和 Agent 主链路稳定性。远程 MCP 涉及服务端配置、凭据管理和连接生命周期，适合在基础验收后单独推进。

    * **安全审核测试样本覆盖不足：** 安全节点已保留在不同模式下，但针对敏感词、意图审核和输出审核的专项测试样本仍需扩展。
    * **原因：** 当前测试更多覆盖路由、工具调用数量、planner tier 和 RAG user_id。安全样本需要按风险类别整理，并确认不会对正常知识库问答造成过度拦截。

未完成项不影响本周完成的主链路能力，但会影响后续质量评估的细粒度程度。后续需要把检索评测、安全样本和 MCP 连接治理拆成独立工作包，避免继续堆叠在 AgentCore 主流程内。

**四、遇到的问题与困难**

* **技术问题：**
    * **Agent 图拆分后容易出现状态语义不一致。** simple、react、plan 三种模式的节点数量不同，消息持久化、trace 下发、工具结果处理和安全审核位置都需要保持一致语义。如果只复制旧图结构，复杂任务可以运行，但简单任务成本过高。如果删减过多节点，观测数据和审核链路会出现缺口。
    * **已尝试的解决方案：** 将三种模式按职责拆分。simple 保留上下文和直答，react 保留工具循环，plan 保留规划与观察状态机。安全审核和最终输出处理作为共同约束维护。前端需要的状态图由后端实际模式驱动，避免 auto 阶段显示错误图形。
    * **需要帮助或待解决：** 暂无外部阻塞。后续需要补充更多模式切换用例，覆盖同一 session 内先简单问答再复杂检索的场景。

* **技术问题：**
    * **工具结果进入上下文后容易放大请求压力。** 知识库检索、联网搜索和文件读取工具都可能返回较长文本。多轮会话中若完整保留每次 ToolMessage，模型输入会迅速膨胀，进一步引发连接错误、限流或 token 超限。
    * **已尝试的解决方案：** 在 ModelDecisionNode 入模前压缩 ToolMessage，并限制单轮工具调用数量。对超长文件读取返回前 6000 字符并提示精确续读，对超出单轮上限的工具调用延后处理。这样保留了可继续执行的信息，又控制了模型入参规模。
    * **需要帮助或待解决：** 后续可增加节点级 token 估算与日志统计，便于定位具体是哪一类工具结果造成上下文压力。

* **技术问题：**
    * **引用来源必须和模型实际使用内容一致。** 早期只要 RAG 召回了片段，就可能全部挂到回答下方。这样会让用户误以为模型使用了所有召回材料，也会降低引用的可信度。
    * **已尝试的解决方案：** 后端要求模型在回答中标注引用号，并在最终 assistant 消息中根据正文实际出现的引用过滤 `used_citations`。自动 RAG 和知识库工具召回统一进入 `citation_map`，历史消息不再复用当前轮来源。
    * **需要帮助或待解决：** 仍需继续观察模型偶发不按引用格式输出的情况，并准备格式修复或兜底提示。

* **非技术问题：**
    * 本周 AgentCore、RAG、工具注册表、知识库入库和安全审核多条链路同时变化，单个改动经常牵动后端状态、前端观测和测试样例。上下文切换成本较高。
    * **已采取的措施：** 继续使用 `CHANGE_HISTORY.md` 记录按日期完成的工程事实，并围绕 Agent Loop、RAG 引用、知识库入库和 OCR 状态语义进行分块整理。对容易回归的 user_id 召回作用域、小模型 tier、delta 追加和工具调用数量补充回归测试。

**六、心得体会与学习收获**

* **本周学习到的新知识和技能：**
    * 对 LangGraph 在真实业务中的模式拆分有了更具体的认识。一个 Agent 图可以覆盖很多情况，但覆盖范围越大，简单任务承担的成本越高。将 simple、react、plan 拆开后，系统可以按任务复杂度分配不同的节点链路，状态管理也更清楚。
    * 对 RAG 引用链路的可靠性要求有了更高判断。向量召回命中只是基础，回答中真实使用哪些片段、这些片段属于哪个用户和哪个知识库、最终消息保存了哪些引用，都会影响系统可信度。引用溯源不能只做展示层处理，后端必须保存可追溯的结构化 metadata。
    * 对工具调用上下文控制的理解更深入。工具越多，模型越容易在单轮中发起过量调用。工具结果越长，后续轮次越容易出现上下文膨胀。统一注册表解决的是能力入口问题，调度约束和结果压缩解决的是稳定运行问题。

* **对项目或开发流程的思考：**
    * Agent 后端的开发需要把可运行、可观测、可控制和可追溯分开衡量。第一周完成的是可运行，本周更多是在补齐后三项。特别是 citation_map、used_citations、observation 决策历史和 ToolMessage 压缩，这些内容很少直接出现在用户第一眼看到的回答中，但决定了系统能否在复杂任务中保持一致行为。

    后端基础设施层的改动还需要保持克制。AgentCore、ContextBuilder、ToolRegistry、RAG 服务和安全审核节点都处在主链路上，任何一个位置的抽象过度都会增加调试成本。本周的改动尽量围绕现有模块加能力，避免在验收前引入新的跨层结构。

* **自我改进方面：**
    * 后续需要进一步增加测试先行比例。对于 user_id 作用域、小模型 tier、引用过滤和工具调用数量这类问题，人工验证容易遗漏，回归测试更可靠。
    * 文档表达需要继续贴近代码事实。周报和总结中应明确区分已完成、已维护和仍需评测的事项，避免把框架能力描述成已经充分验证的质量结论。
