**三、 未完成工作及原因**

* **未完成任务列表：**
    * **gRPC 自动化测试覆盖仍不够细：** 目前已经梳理 REST 与 gRPC 的接口对应关系，也确认了 `protos/agent_service.proto` 和 `agent_service/api/grpc/servicer.py` 的主要职责，但 gRPC 侧自动化断言没有 REST/SSE 部分细。
    * **原因：** gRPC 测试需要构造 protobuf 请求对象，并准备可控的服务端或 mock 环境，测试准备成本比普通 HTTP 接口更高。本周优先保障前端实际调用频率最高的 REST、SSE 和知识库接口，因此 gRPC 部分主要完成结构梳理和对应关系说明。
    * **真实模型链路测试不能完全自动化：** `agent_service/scripts/test_small_model.py` 可以用于模型连通性检查，但真实模型调用依赖本地 API Key、Base URL、网络和服务限流情况。
    * **原因：** 自动化测试如果依赖真实外部模型服务，结果容易受环境影响，不适合作为稳定回归测试。因此模型连通性更适合放在本地验收或人工检查中，自动化测试主要通过 mock 避免外部依赖。

**四、 遇到的问题与困难**

* **技术问题：**
    * `/agent/stream` 是 SSE 流式接口，不是普通 JSON 接口。测试时不仅要看状态码，还要检查 `data: <json>\n\n`、`data: [DONE]`、`delta`、`error`、`context_builder`、`tool_trace` 等事件是否能被前端正确解析。
    * **已尝试的解决方案：** 将流式接口测试拆成参数检查、SSE 格式检查、前端 store 解析检查三部分，通过 mock chunk 降低真实模型调用对测试稳定性的影响。
    * **需要帮助或待解决：** 后续如果继续完善测试，可以补充更系统的 SSE 边界场景，例如中途取消、服务端异常、空内容 chunk、重复事件等。

* **技术问题：**
    * console 和 editor 共用同一套后端，但接口使用重点不同。console 偏 Agent 对话和观测，editor 偏知识库文件、附件、图谱、灌库和文档引用，容易在整理 API 时混在一起。
    * **已尝试的解决方案：** 分别从 `console/src/router/api_routes.js` 和 `editor/src/router/api_routes.ts` 入手，把两套前端的接口按使用场景分类，再反向对应到后端 REST 文件。
    * **需要帮助或待解决：** 无。当前已经能够区分两套前端的主要 API 范围。

* **技术问题：**
    * 知识库文件上传和 Agent 附件上传名称相近，但后端处理逻辑不同，容易导致测试断言设计不准确。
    * **已尝试的解决方案：** 将 `/knowledge/files/upload` 和 `/agent/attachments/upload` 分开整理。知识库上传关注文件树、预览、灌库和搜索；Agent 附件上传关注 session 绑定、attachment_id、上下文注入和前端附件展示。
    * **需要帮助或待解决：** 无。后续只需要在测试用例中保持这两个接口的断言边界。

* **非技术问题：**
    * Sprint 2 收尾阶段材料较多，接口文档、测试报告、质量门禁、压测材料和代码文件容易混杂，查找时效率不高。
    * **已采取的措施：** 按“前端 API client、后端 REST、gRPC/proto、tests、docs 验收材料”的顺序重新归类，答辩和自查时按链路说明，不再零散背文件名。

**五、 心得体会与学习收获**

* **本周学习到的新知识/技能：**
    * 更清楚地理解了 REST、SSE 和 gRPC 在项目中的不同使用场景。REST 适合普通请求响应，SSE 适合 Agent 流式回答和观测事件，gRPC 更适合外部服务或非 Web 客户端调用。
    * 熟悉了前端 API client 与后端接口之间的对应关系，尤其是 `/agent/stream`、`/sessions`、`/settings`、`/knowledge/*` 和 `/agent/attachments/upload` 这些核心接口。
    * 理解了测试分层的意义。单元测试关注模块逻辑，API 测试关注接口契约，前端测试关注 store 和组件状态，E2E 测试关注真实用户流程。

* **对项目或开发流程的思考：**
    * 测试与 API 对接处在前后端之间，是最容易暴露问题的位置。前端页面显示异常，可能来自组件状态，也可能来自 API 参数不一致、后端返回结构变化或流式事件解析问题。
    * 在 Agent 项目中，接口测试不能只验证“接口能返回”。因为 Agent 接口往往包含流式数据、工具调用、观测 trace、模型模式、引用来源等信息，测试时需要关注整个链路的稳定性。
    * 对于 console 和 editor 这种双前端项目，API 对接必须按业务场景拆分。只看某一个前端会遗漏另一端真实使用的接口。

* **自我改进方面：**
    * 后续在类似项目中，需要更早建立接口清单和测试点清单，把接口路径、请求参数、返回结构、前端调用位置和异常场景放在一起维护。
    * 对流式接口、文件上传、知识库灌库和 gRPC 这类复杂接口，需要提前设计 mock 和断言方式，减少对人工演示和真实外部服务的依赖。
