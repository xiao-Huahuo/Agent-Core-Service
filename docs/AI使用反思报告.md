# AI 使用反思报告
## 1. 使用背景
本项目开发过程中使用了较高强度的 AI 辅助。
使用 AI 的主要原因是项目的功能面扩展很快。后端有 AgentCore、LangGraph、工具注册表、长期记忆、知识库入库、REST 和 gRPC 双接口。前端有桌面工作台、文件树、Markdown 编辑器、代码预览、多模态预览、图谱、搜索页、设置页、Agent 侧边栏和独立 Agent 页。很多问题并不复杂，但它们分布在多个文件和多个层次之间。如果每次都完全手工追踪链路，开发节奏会被大量重复查找、参数传递和类型修正拖慢。 因此，AI 在本项目中的定位更接近高强度开发助手。 AI 使用日志不再另外编写流水账。项目根目录下的 `CHANGE_HISTORY.md` 已经按日期记录了功能新增、问题修复、文档补充、测试补充和调试过程，它比事后重新整理的日志更接近真实开发轨迹。

## 2. 实际参与方式
AI 主要承担四类工作。
- 第一类是跨文件实现。比如引用链路修复同时涉及选区工具栏、聊天输入框、用户气泡展示、前端 SSE 请求、后端消息保存、ContextBuilder 和 gRPC proto。这个问题如果只看前端，很容易停在“输入框能显示引用”这一层，但真正验收时还要确认引用能显示在用户气泡上方，并且进入模型上下文。AI 在这类任务中可以沿着数据流持续追踪，把展示、传输、持久化和上下文注入放在同一个修改链路里处理。
- 第二类是重复但细节多的工程工作。 文件树多选、Ctrl 复制剪切粘贴、拖拽移动、外部文件粘贴、PDF inline 预览、工具注册表页面、搜索兜底、header 进度条，这些功能的业务判断相对明确，但状态分支多。AI 能快速补齐大量样板代码和边界处理。人工仍然需要检查交互是否真的生效。
- 第三类是后端链路补齐。多模态清洗就是典型例子。DOCX、XLSX 和 PPTX 都要按 Office Open XML 读取内部 XML，CSV 和 TSV 要考虑编码和分隔符，HTML 要抽取正文，XML 要保留节点路径，最后还要统一接到 frontmatter 和知识库入库流程。AI 给出的第一版实现缩短了启动成本，后续再靠测试文件和运行反馈修正不稳定点。
- 第四类是文档整理。架构设计、接口设计和数据模型设计都建立在已有代码基础上。AI 先遍历项目，再把实际模块、接口路径、数据表和运行时目录整理出来。这个过程减少了从代码到验收材料之间的转换成本。

## 3. 效果比较明显的地方
原本需要花较长时间查找的跨层调用，AI 可以很快定位到相关文件。例如搜索框按内容搜不到的问题，表面上是前端搜索体验问题，实际涉及 active library 过滤、索引是否及时更新、磁盘全文兜底和语义搜索结果合并。AI 的处理方式不是只刷新索引，而是在后端增加直接读取当前知识库文件内容的搜索兜底，使刚导入或尚未灌库完成的文件也能被搜到。 这类修复更接近工程上的修复。 AI 对“链路断裂”的问题也比较有帮助。本项目出现过多次这种情况：页面上看起来有功能，真正的数据没有进入下一层。引用显示在输入框里，但用户气泡不显示，模型也没有读到引用。工具注册表页面存在，但请求到了前端 HTML，JSON 解析报错。PDF 预览接口能返回文件，但浏览器把它当成下载。长期记忆能写入，但长期规则如果仍走 RAG 召回，就不能保证每轮必读。AI 在连续处理这些问题时，能把现象和先前修改联系起来，减少重新理解上下文的时间。
项目早期像一个后端 Agent 服务，后期逐渐形成了包含编辑器、知识库、搜索、图谱、观测、独立 Agent 页和多模态预览的综合工作台。这个跨度较大，如果没有 AI 辅助，很多小功能可能只能停留在 TODO。
## 4. 不足和风险
AI能写出一个组件、一个接口或一个服务函数，但真实项目里还存在开发环境、打包环境、Electron 环境、浏览器安全策略、后端 CORS、文件路径、用户 active library 等条件。`Unexpected token '<'` 就是这种问题的典型表现，接口调用实际拿到的是前端 `index.html`，单看返回处理代码不一定能发现。
另一个风险是”测试幻觉”,它可能过早相信自己的修改已经生效。比如 UI 间距、按钮位置、主题适配和引用块显示，代码改了不代表视觉上改对了。用户反馈”没动””没看到引用块”时，必须回到真实界面表现和具体 DOM 状态验证，只根据 diff 判断是不够的。
AI 对项目规范也需要约束。本项目要求 UTF-8、要求修改后写 CHANGE_HISTORY、要求前端主题走全局变量、要求 REST 和 gRPC 尽量同步、要求不要用运行时文件偷懒绕过代码问题。AI 如果没有被明确提醒，可能写出短期能用但后续难维护的实现。尤其在 Windows PowerShell 环境中，中文文件显示和读写存在编码风险，不能直接相信终端里看到的乱码内容。
还有一个实际发生过的问题：工作目录判断错误。 这类错误来自执行环境。文档曾经被写入相邻目录，后来通过路径检查、移动文件和清理误写目录修正。这个问题提醒我，AI 每次创建文件后都必须用实际绝对路径和 `git status` 确认，不应只凭当前对话中的项目名判断。

## 5. 对开发流程的改变
使用 AI 后，开发流程从“慢慢写一个点”变成了“快速改一条链，集中验证”。 有明显收益，也带来新的压力。AI 一次可能修改多个文件，功能推进速度快，但任何一个字段名、路径、事件名、类型定义或接口参数不一致，都可能让整个链路失效。以前手工开发时，错误通常更局部。AI 辅助开发时，错误可能藏在链路中间，直到真实点击、上传文件或发起对话才暴露。 所以验证变得更重要。
本项目比较有效的做法是先让 AI 读代码并说明判断，再执行最小必要改动，然后运行类型检查、相关测试或至少做静态检查，最后根据实际 UI 和后端日志继续修正。这个流程比让 AI 直接“大改完”可靠得多。尤其是多模态、搜索、引用、工具注册表这些功能，只有把前端、接口、服务和数据层连起来看，才能确认它们真的完成。
测试也因此变得更有价值。多模态清洗有测试文件，搜索兜底有回归测试，工具注册表有注册表来源测试，气泡引用有组件测试。AI 能快速补测试，但测试本身要由人判断是否覆盖真实用户路径。否则测试会变成只证明当前实现没有语法错误。

## 6. 对项目质量的影响
AI 提高了项目完整度，但没有自动保证项目质量。项目质量最终取决于边界是否清楚。多模态能力目前主要是文本提取、结构化、预览和入库前处理，还不能宣传成完整 OCR 或视觉理解。长期记忆和长期规则必须分开，前者可召回，后者每轮必读。工具注册表要来自最终注册表，不能只列内置工具。搜索要承认索引存在延迟，因此需要磁盘全文兜底。PDF 预览要明确 inline 返回，避免 Electron 或 Chromium 把它下载。 这些判断需要人来做。
AI 的优势是执行这些判断。 在开发中，AI 经常把原本临时的修复做成较稳定的结构。例如长期规则没有继续塞进长期记忆，而是新增写系统提示词的工具。搜索没有只刷新页面，而是在后端补充未索引内容的直接搜索。多模态入库没有让每种格式各自走一套流程，而是统一到 StructuredKnowledgeDocument 和 frontmatter JSON。这样的结果对项目结构是有帮助的。

## 7. 对 AI 使用方式的反思
1. 给 AI 的任务必须足够具体: “修一下搜索”这种描述太宽泛，而“按内容搜却搜不到，有时候明明看到内容在里面”就能指向索引延迟、磁盘内容读取和搜索结果过滤。类似地，“引用块看不到”比“优化引用功能”更能帮助定位用户气泡和历史消息展示。
2. 日志非常关键: `OPTIONS /agent/tools 405`、`Unexpected token '<'`、`422 Unprocessable Entity`、`Connection error`、`429 Too Many Requests` 这些信息直接决定排查方向。没有日志，AI 只能根据代码结构推测，成功率会下降。 复杂任务应先读项目。 多模态入库和设计文档都证明了这一点。如果没有先遍历目录、模型、接口和前端结构，AI 很容易写出通用模板。先读项目，再写代码或文档，输出会更贴近真实实现。
3. 文档要约束风格: AI 默认文风通常段落过于均匀，句式也容易整齐。验收文档如果全部这样写，会显得不自然。通过明确要求专业语气、段落长度变化、少用套话、禁止某些固定表达，文档会更接近人工整理后的技术说明。

## 8. 后续改进方向
后续继续使用 AI 时，需要把检查流程固定下来。前端修改至少做类型检查，后端修改至少跑相关 pytest，涉及接口的修改要同时检查 REST、gRPC、前端 API client 和 proto。涉及文件系统的修改要检查路径越界和用户已有文件。涉及文档的修改要检查文件是否写入正确仓库、链接是否有效、图表是否能渲染、禁用词是否出现。
AI 使用日志也可以进一步整理。当前 `CHANGE_HISTORY.md` 作为真实日志是合适的，但由于历史上有编码显示问题，直接提交给验收老师阅读可能不够友好。可以保留它作为原始日志，再补一页索引，按功能实现、问题修复、测试补充、文档生成四类列出关键日期和对应条目。
最后，AI 更适合做受控的高强度辅助开发。项目方向、能力边界、验收口径和最终取舍仍然要由开发者判断。本项目能推进到目前状态，主要依赖明确需求驱动，再由 AI 快速实现、补齐链路和生成材料。这个模式适合课程项目，也适合早期原型，但不适合无人审查地直接合并所有生成结果。
